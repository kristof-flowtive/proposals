01 — Understanding

What you're solving for

Your operators work on heavy industrial sites with gloves on, often with no signal, and the app has to keep working anyway. Most mobile bids will reach for a cloud speech API and a hosted sync service and quietly fail your third requirement. The brief is really a constraint: everything core runs on the phone, and the network is a convenience, not a dependency.

Requirement

"Fully functional with zero cellular connection"

SQLite on the device is the source of truth. Every screen reads and writes locally; a sync queue replays changes when a connection appears. Airplane mode is a test case, not an edge case.

Requirement

"Localized device CPU/NPU processing, zero external web dependencies"

Speech uses Apple's on-device recognition and Android's on-device recognizer. The overlay uses ARKit and ARCore. No third-party SDK sits in the path of a core tool, so there is nothing to phone home and nothing to expire.

Requirement

"Daily code pushes" and "clickable builds via TestFlight"

A commit to your private ITG repository every working day, on a dated branch merged at each milestone. A TestFlight build every Friday from day five, with an Android internal-testing build alongside it.

Requirement

"Glove-friendly UI trigger"

A single oversized press-and-hold control, high contrast, with haptic confirmation, so a gloved hand can start and stop dictation without looking. Also mapped to the volume-up button as a hardware fallback.

Confidentiality and firewall

ITG Platforms LLC only. No tracking, no location logging, no stakeholder references.

No analytics or crash-reporting SDK unless you ask for one. Location permission is never requested in the foundation build. Nothing about field sites, founders or stakeholder metrics is written to logs, commits or test data. Branding, bundle identifiers and store listings carry ITG Platforms LLC and nothing of mine.

04 — In the field

Built so a dead zone never costs an operator a bid

01

Local first, always

Writes commit to SQLite before anything else happens. If the phone dies mid-entry, the last saved field is still there on restart.

02

Speech works in a basement

Recognition is forced to on-device mode. If a device cannot support it, the app says so at setup rather than silently falling back to a server.

03

Overlay degrades honestly

If plane detection cannot lock (poor light, reflective surface), the overlay switches to a manual two-corner pin mode instead of drifting.

04

Purge never deletes the only copy

The scrub script keeps the newest version of each drawing set and anything not yet synced, whatever the retention window says.

05

Paid users stay paid offline

Entitlement is cached with a grace period, so a Premium operator in a dead zone is not downgraded to Basic by a missed Stripe check.

06

Yours, in your accounts

Apple Developer, Play Console, Stripe and the repository all stay under ITG Platforms LLC. I work from invitations you can revoke the day we finish.

You'll see a test subscription on each tier, the board filtering live bids, and a priority email arriving from a blast queued while offline.

07 — The same pattern, elsewhere

Two worked examples of this architecture

Illustrative scenarios, not client case studies. They show how the same building blocks, a local database as source of truth, a replayable sync queue and on-device processing, bend to other field businesses.

Worked example · Utility inspection crews

Pole inspections dictated in the field, filed when the truck reaches town

Inspectors work rural lines with no coverage for hours. Each inspection is dictated on-device into a structured form, photos attach to the record, and everything sits in SQLite until the truck is back in range. The sync queue replays in order, the office sees the day's work by evening, and nothing was ever typed with cold hands.

08 — Before kickoff

Three things I'll confirm on our first call

Q1
What does the sync queue replay to?
The brief covers the device side. If there is no backend yet, I'll default to a minimal endpoint spec you own and can host anywhere, and the app will be complete without it.
Q2
Which devices will operators actually carry?
On-device speech and AR need relatively recent hardware. I'll assume iPhone 12 or newer and ARCore-certified Android, and tell you before milestone two if a target device falls short.
Q3
Whose mail account sends the priority blasts, and which Stripe account?
Both should be ITG's. I'll need SMTP credentials and a Stripe test key at milestone four, nothing earlier.
