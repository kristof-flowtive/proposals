01Understanding

What you're solving for

The hard part is done: your prompt is finished and tested in person. What you need is the app around it, one that feels like a polished product, not a chat window, takes payment, hands out codes, and carries someone through 45 to 60 minutes on their phone without losing a word.

That length is the real design constraint. Over an hour, phones lock, tabs close and signal drops. So the server, not the browser, holds the conversation: each answer is saved before the next question is asked, and the report is generated by a background job that finishes and emails itself even if nobody is watching the "preparing your results" screen.

You asked for"Answers typed, or spoken using the device's built-in dictation, and editable before sending"

A plain, roomy text box that works with the microphone on the iPhone and Android keyboard. Nothing to install or allow, and every word is editable before it is sent. In-browser speech recognition is patchy on iPhone, so it isn't built in place of the keyboard's own dictation.

You asked for"If the connection drops or the phone dies, the same code resumes where they left off"

The code is the key to the session. Re-entering it on any device loads the full transcript and shows the last unanswered question. A half-typed answer is kept on the device as a draft too.

You asked for"The prompt and model kept in a settings file I can change without touching code"

One settings file holds the prompt, the model, the time limit and the report sections. It is checked when you save it, so a typo can't take the live app down, and every version is kept so you can roll back.

You asked for"the report on screen, as a PDF, and by email, in one consistent branded layout"

Claude returns the report as labelled sections (title, key statement, profile and the rest of your structure). One designed template renders them on screen, as the PDF and in the email, so all three always match.

Not in your brief, but it protects your margin and your prompt

Your prompt never reaches the browser, and the long conversation stays cheap

The prompt is your product, so it lives only on the server; the browser sees questions, never instructions. Prompt caching means the fixed prompt and the growing transcript are re-read at a small fraction of the normal input price each turn, which keeps an hour-long session around a dollar. Admin shows the actual cost of every session from Claude's own usage figures, not an estimate.

04Reliability

Built so a paid assessment is never lost halfway

01

The phone dies at question 30

Every answer is saved before the next question is generated. The same code on any device resumes at question 30, with the transcript intact.

02

They close the results screen

The report is built by a background job, not by the open page. It finishes anyway, is stored, and arrives by email with the PDF.

03

Claude is slow or briefly down

Requests retry automatically. If a question still can't be generated, the buyer sees a calm "try again in a minute" and their answer is already saved.

04

A payment is disputed or refunded

Refunds from admin go through Stripe and disable any unused codes in the same step, so a refunded code can't be started.

05

A prompt edit breaks the report

A report that doesn't match your section list is retried once, then held and flagged to you, never sent half-formed. Rolling the settings back takes one click.

06

You decide to move on from me

Code in your repository, services in your accounts, a handover guide and a walkthrough. Any developer can pick it up.

08Before kickoff

Three things I'll confirm on our first call

Q1

How long should a code stay valid, and what counts as "expired"?

It decides the reminder email and the reopen button. Default: 14 days from first use, unused codes valid for a year.

Q2

Should a two-pack buyer be able to give the second code away?

Default: yes. The second code works for anyone, and its first-name screen captures who used it.

Q3

Which model did you test the prompt on?

The app should launch on the same model you tested in person, so the report reads as you expect. Default: that model, set in the settings file, with cost compared against Sonnet 5.5 during beta.
