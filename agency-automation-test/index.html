01 — Understanding

What you're solving for

You want your team to "handle more clients with less operational drag", and you've got a list: an AI Website Generator, data pipelines, campaign dashboards, fulfilment agents, onboarding and off-boarding. You also want to find out whether a developer is any good before committing. A test project should answer that, and should leave you with something you'd have built anyway.

Requirement

"Test tasks, scope and fixed project price agreed upfront"

So here is one, scoped and priced. If you'd rather hand me your own test brief, the same rate and milestone structure apply and I'll price it within a day of reading it.

Requirement

"Data pipelines into our database and related dashboards"

The test is exactly that: ad platform data into Supabase on a schedule, then internal and client-facing views on top. It's the base most of your other projects will read from.

Requirement

"Routers, webhooks, API calls, error handling"

Make.com runs the schedule and routes by client. Where a Make connector is thin, a small Python job on Railway calls the API directly. Every failure lands in an errors table and a Slack message, not in a scenario history nobody opens.

Requirement

"GitHub for version control"

Python, SQL migrations and the Make blueprints all live in your GitHub from the first commit, written with Claude Code, so the next developer can read how it works.

03 — Your controls

Adding a client is a row, not a ticket

Your account managers add or pause clients in one Supabase table. The next morning's run picks it up. Nobody opens Make.

  • ▸clients: name, ad account ids, target CPA, active
  • ▸campaign_daily: one row per client, day, campaign
  • ▸client_notes: the weekly Claude note, editable before a client sees it
  • ▸errors: what failed, for which client, and whether the retry worked
